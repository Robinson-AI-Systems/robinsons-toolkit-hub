# Hub-initiated MCP connection compatibility profile — October 18, 2026

**Purpose:** Give every future independently usable Robinson MCP server the **same** connection specification. The Hub is the MCP **client**, initiating discovery, delegated OAuth authorization, authenticated tool discovery and routing. No backend discovers, calls, or registers itself with Hub. No custom provider adapter in Hub. This profile augments the existing RTC 1 contract rather than silently changing its pass-only HTTPS API. Any incompatible provider needs a reviewed adapter or an explicit future contract revision, not a weaker OAuth guard.

## Required server interface for new production Hub connections

1. Public globally routed **HTTPS** service origin. RTC 1 `GET /api/contract` truthfully advertises `rtc:1`, canonical unique `server`, tool `prefix`, bounded `areas`, `profiles`, `modes` (including LIVE), `counts` and current version. It exposes independent MCP `POST /api/mcp` with `tools/list` and `tools/call`, all tool names beginning with its prefix, and accurately marked read/write/tool risk metadata. Direct MCP clients must continue to work without Hub.
2. `/.well-known/oauth-protected-resource` or the MCP endpoint-specific RFC9728 location responds with a `resource` equal to exact `https://service.example/api/mcp` and the issuer in `authorization_servers`. The server's own 401 `WWW-Authenticate` should also point to that resource metadata per MCP HTTP authorization. The Hub does not learn issuers by guessing a provider brand.
3. The authorization issuer provides RFC8414/OIDC discovery, `authorization_endpoint`, `token_endpoint`, PKCE **S256**, `authorization_code` and an actual client onboarding method. Initial universally testable path uses RFC7591 dynamic client registration with `client_secret_post` or `none` supported. Newer Client ID Metadata Documents are the preferred compatibility addition; source currently handles DCR first. Do not confuse public client registration with user consent.
4. The user—not a development agent or the Hub—authorizes the chosen server and exact account. Authorization requires `response_type=code`, PKCE S256, random state, an exact pre-registered HTTPS callback, and RFC8707 `resource` in both authorization and token requests. The issuer must bind tokens to the intended MCP resource. Service consent should accept `profile`/comma-separated `areas` and the actual provider's `scope` parameters where supported. No Hub form may mint an issuer token or silently widen authorization.
5. Access tokens are accepted only by their issuing MCP resource through `Authorization: Bearer`, never in query strings. The issuer should return `expires_in`, `token_type: Bearer`, and rotating `refresh_token` for durable consent; if refresh is not offered, the connection truthfully requires reconnect. On refresh, retain or narrow account, mode, profile, areas, scopes and issuer; never silently widen.
6. A service supplies truthful scoped identity via its protected RTC whoami/MCP tool so Hub can verify consent-selected mode, profile, principal/account and areas. Returned tools are inspected on demand; Hub enforces caller-selected policy in addition to issuer tool guards. Write/money/destructive actions still use provider-owned authorization, dryRun/confirm/readback/audit and user-selected approval policy.
7. Server independently enforces OAuth rate limits, revocation, tenant isolation, account consent, permissions and token lifetime. Hub maintains per-owner + per-caller-family isolated encrypted credentials and one-time consent transactions; no bearer, refresh, DCR client secret, identity or provider data in chat, public docs, PRs or logs. The client cannot elevate one Hub caller with another caller's OAuth access.

## Hub end-to-end workflow

`owner enters HTTPS origin → Hub probes /api/contract and OAuth metadata → verifies identity and chooses exact Hub user connection → Hub registers itself via the issuer's advertised DCR → user sees issuer-owned sign-in/consent → issuer redirects once to Hub's random-state/PKCE callback → Hub trades code with resource binding → Hub validates real authenticated MCP tools/list and caller → Hub stores issuer tokens AES-GCM with owner/caller-family isolation → agent uses Hub fixed dynamic broker → Hub refreshes through the same issuer when allowed, or requests fresh consent → disconnect/revoke`.

**Legacy distinction:** RTC 1 HTTPS passes and `hub_server_grants` remain an explicit legacy/manual test and standalone HTTPS compatibility path. They are *not* the desired production onboarding or a prerequisite for the OAuth-native Hub client. Do not delete historical grants/migrations while existing callers use them; retirement needs usage readback, independent consent migration, rollback and separate approval. Never resurrect expired TEST passes to fake LIVE continuity.

## Current implementation/acceptance truth

The initial Hub source workflow provides Hub-owned discovery, DCR, PKCE/browser consent, one-use state, encryption, token exchange, user-visible connection metadata, eligible refresh and actual read-only MCP tools/list verification. The existing H-3 federated broker remains pass-backed and **must be extended** to execute search/describe/call/batch using these OAuth connections before one Hub chat connection can fully operate newly OAuth-linked providers. Do not claim production routing or Workspace LIVE acceptance from owner browser login or synthetic tests. Hosted schema migration 025, exact-Hub deployed readiness, REAL issuer OAuth consent and current Workspace tool/denial/refresh continuity all remain separate release and acceptance gates. Any additional auth issuer origin/metadata modes, SSE session continuity, multiple issuers, Client ID Metadata support, and production-grade remote revocation need separate tested behavior rather than assumed support.
