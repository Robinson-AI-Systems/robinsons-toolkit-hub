## First implementation boundary — PR #158

After #157 merged on `d223de4857265cc29b825c43c07ad32708074a23`,
the first H-3 source slice extends H-2's socket-time DNS-pinned, hostname
certificate-verified, no-redirect TLS transport to **GET only**

DNS rebinding and no path-based redirect bypass.

dashboard; it cannot execute tools. Exact deployment pin, real upstream TEST

## Fourth implementation boundary — Hub RTC HTTPS parity (proposed)

The native fixed-menu `/api/mcp` source read path is already guarded,
but the directly exposed RTC HTTPS `/api/tools` list, item and batch
handlers still accepted only Hub-owned tools. This change lets authenticated
TEST Hub callers with an independent eligible upstream grant search and
describe RTC tools with GET, execute approved harmless reads via POST, and
execute mixed Hub/RTC read-only batches through the **same**
`runFederatedBroker` used by native MCP. It neither creates a second
provider dispatcher nor permits broad grants. Schema remains on demand.

Request authentication/rate-limit checks precede any network or schema call.
The HTTP layer uses bounded validated selectors/body/result and returns
safe explicit refusal codes. Runtime grant revocation, caller, origin, prefix,
readOnlyHint and durable audit checks remain in the shared federation
function, including no retry of ambiguous POST outcomes. The unchanged
Hub-only catalogue/reads retain their compact response contract. Synthetic
handler-level tests exercise GET search, GET schema, POST read, mixed batch,
missing grant, unsafe write metadata, LIVE/write caller denial, oversize
and uncertain outcomes.

Acceptance matrix: (1) exact-head CI/SQL green; (2) independent review of
safe HTTP behavior and all changed tests; (3) checked future deployment;
(4) exact Hub actor and two service revisions verified independently;
(5) authenticated benign reads, refusal and grant revocation through both
MCP and HTTP readbacks. Only source/tests are proposed in this PR; (3)–(5)
and hosted migration 008 are not claimed. Large caller/grant-bound
result handles/pagination and full scale/RTC1 remain H-3 follow-ups.


## Fifth implementation boundary — grant-checked encrypted RTC result pages (proposed)

Forwarded read results >8KiB now enter a dedicated, short-lived one-hour
encrypted result store (new additive migration 009) instead of silently
truncating or returning an arbitrary unavailable response. Hard maximum
64KiB; above that is explicitly refused. Stored bytes are encrypted
AES-256-GCM with owner/caller/grant/service AAD and hashed random handles.
Results are 4KiB byte pages with base64url encoding for accurate UTF-8
reassembly. Both text and structured MCP results remain under the existing
8KiB bound; `hub_call(name=hub_result_read,args={handle,page})` returns a
page without contacting the provider. Existing pass-authenticated
`/api/results/{handle}` also accepts RTC-prefixed handles without changing
H-1's old records. Every RTC page checks the live exact caller grant and
server before decrypting: expiry, caller change, grant replacement/revocation
or server disablement refuses the read. Any uncertain upstream POST remains
one-shot and is never retried.

Synthetic tests cover positive multi-page reconstruction, SQL ciphertext
and raw-handle exclusion, exact caller/owner isolation, missing/changed
grant, expired/tampered handle, immutable per-call audit and refusal
above 64KiB. Hosted 009 installation, two-service authenticated result
paging with same-grant revocation, RTC1 and scale evidence remain OPEN.
The fixed seven-tool Hub public MCP catalogue is unchanged.


## Sixth implementation boundary — resumable RTC discovery and scale (proposed)

Prior discovery searched only three services per call, with
`incomplete: true` and `next: null` even when more authorized providers
existed. Bounded continuation now provides a five-minute HMAC-signed
opaque cursor bound to original query, exact caller, mode/profile and
current authorized service roster. Each page independently selects and
re-resolves at most three active caller grants, preserving partial provider
failure isolation and on-demand schema only. Missing or invalid secret,
expired/tampered cursor, changed caller or revoked/changed roster fail
closed. For small user limits, cursor advances by actual scanned services;
Hub-owned result metadata is returned only on the first page.
HTTP GET search and native fixed seven-tool MCP broker share the same
continuation behavior. Source accepts up to 100 authorized metadata
entries without eager upstream schema fan-out; per-request response
budget is bounded below 8KiB. A query too broad within one upstream
retains explicit incomplete status and may require narrowing to that
specific server. This PR does not promise upstream pagination for one
service's entire catalog.

Automated synthetic matrix tests cover 2/5/12/50/100 service fleets
with 100 advertised tools each (10,000 total at 100), bounded
schema-independent fan-out, measured elapsed latency and RSS deltas;
read/write execution, hosted migrations and real two-service connected
acceptance are separately OPEN. No production deployment or spending.


## Seventh implementation boundary — complete bounded namespace browsing (proposed)

The Hub namespace view previously inspected only 50 services and could
overflow its ~8KiB response budget as the authorized fleet grew.
`hub_namespaces({limit,cursor})` now lists a bounded page of 1–20
eligible service metadata entries (10 by default) with an expiring
HMAC-signed continuation bound to the exact caller and current
authorization roster. Hub metadata occurs only on the first page.
No upstream providers are called for namespace listing, so tool
catalogues remain lazily inspected. The `hub_health` eligible service
count now agrees up to 100 services. Unknown, stale or tampered
continuations refuse without leaking authorized service membership.
Synthetic unit tests traverse 2/5/12/50/100 rosters fully, including
one-entry pages; the RTC contract's full real/provider acceptance and
DB migration installation are still separately OPEN.

## H-3 metadata revocation race (PR #174 source; hosted proof pending)

All authenticated selective discovery and schema GETs now re-resolve the exact
owner/caller grant after the upstream HTTP response before disclosing provider
metadata. Replaced, expired or revoked grants fail closed without returning the
old provider's names or schema; a failed provider stays isolated, and a search
page explicitly reports incompleteness. Regression cases exercise revocation,
grant replacement and no provider execution. Remote authenticated two-service
TEST acceptance remains OPEN in the release queue; CI is not provider proof.

## H-3 in-flight provider read revocation (PR #175 proposal)

After a provider RTC POST completes and the durable outcome is recorded, Hub
re-resolves the current caller's exact active upstream grant before returning
either inline JSON or an encrypted result handle. Revocation, replacement or
failed reauthorization withholds successful provider payloads; POST is never
retried and the final check is also the storage authorization. Actual remote
revocation and provider readback remain acceptance-queue items, not source proof.

## H-3 bounded multi-read batch replies (PR #176 proposal)

A caller can use the same sequential guarded Hub broker for up to ten RTC
TEST reads while keeping a fixed 20-second batch processing budget and 10 KiB
aggregate result budget. Unexecuted suffixes and the first over-budget
completed read receive explicit per-call unavailable results and
`incomplete:true`; the Hub does not truncate a successful upstream payload,
automatically retry any RTC POST, or dispatch further calls after exhaustion.
Native and HTTPS behavioral tests cover deadlines, large responses, audited
single-attempt execution and total output bounds. This is not hosted proof.

## H-3 encrypted forwarded-result lifecycle (PR #177 source)

Expired RTC forwarding result handles now undergo bounded opportunistic
garbage collection on actual new RTC-result storage, rather than consuming
Neon's capped storage indefinitely after the one-hour expiry. Only the
dedicated H-3 encrypted handle table is touched, at most 100 expired rows
per write, in expiration order with deterministic ties. Caller reauthorization,
existing H-1 result tables, TTL, encryption and output bounds remain
unchanged. Real disposable Postgres fixtures assert expired-only collection,
batch limits and continued active-handle retention; hosted behavior remains
separately queued until checked release and genuine TEST activity.

## H-3 TEST grant/endpoint-bound search continuation (PR #179 proposal)

The native and HTTPS search and namespace cursors now bind not just to
the owner/caller and permitted roster but also to each active grant's
immutable identity, verification time and actual configured origin.
Revoking/reissuing a grant or replacing an upstream destination invalidates
previous signed continuations even when the service name, prefix and areas
are unchanged. No pass bytes, grant identity or target origin are embedded
in the returned cursor; they are inputs only to the server-held HMAC scope.
Synthetic cursor replay and isolated real PostgreSQL selection tests cover
the same-area replacement; provider credentials and network calls remain
separately guarded. Real deployed TEST acceptance stays OPEN.

## H-3 owner-confirmed TEST service retirement (PR #180 proposal)

An independently password-verified Hub owner can explicitly type RETIRE
for an exact staged/active RTC service. One PostgreSQL transaction locks the
owner's server, disables its routing and revokes all still-unrevoked
caller-scoped upstream TEST grants. It returns only a count and preserves
encrypted historic records, durable audit and service ownership. Failure
rolls back both operations, with no provider requests or secret disclosure.
Real disposable PostgreSQL and owner-form tests cover authorization,
isolation, rollback, idempotence and blocked dispatch. This provides
bounded fixture deactivation for future H-3/D-4 acceptance; it does not
pretend deployed service TEST acceptance has passed.
