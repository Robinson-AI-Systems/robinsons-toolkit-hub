## Drift check A
- `rtool` already resolves standalone RTC service passes and uses `send` for scoped HTTPS; reuse its authenticated transport.
- `packages/cli/src/local-browser.js` is headless, read-only, origin-allowlisted L-3. A guided owner browser must be **visible**, isolated, and explicitly owner-driven; do not reuse the headless screenshot routine as an interactive browser.
- RTC §11 already defines `<prefix>_where_is_setting(query)` and `{setting,url,steps,expected,verifyWith?}`. Step text is untrusted presentation, never executable JavaScript, browser selectors or tool arguments.
- Neither a browser launch nor an owner's click is provider readback. Verified `verifyWith` requires exact safe discovery and a separately authorized server read, otherwise report UNVERIFIED.

## Security and complete acceptance
- `rtool guide <server> "<setting>"` obtains the signed-in service's structured §11 instructions via independently scoped HTTPS and validates capped shape, origin, steps and optional verifier.
- Open one **visible** browser; the owner signs in, types any secrets themselves, approves each displayed step individually, and may cancel at any step. The agent does not type/capture credentials, grant background navigation, or click through provider settings on the owner's behalf.
- No untrusted instruction supplies a tool name to execute without independent exact advertised read-only verification. `verifyWith` is a read-only server-scoped call and exact field comparison; absent/inaccessible/mismatched evidence stays NOT VERIFIED; never claim a write success from instructions.
- Validate malformed/hostile steps, cross-origin URLs, credential-shaped text and unexpected verifier actions; refuse rather than run. Positive and cancel tests must prove browser closing and zero unapproved calls. CLI integration through original `runCLI` and independent fault/error paths.
- Keep standalone server behavior, current end-user authority, developer TEST gates and all Hub production settings unchanged.
